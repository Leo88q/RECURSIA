# Эксплуатация: ключи, проверяемая сборка, bug bounty, аудит, инциденты

Документ для студии. Технические шаги развёртывания — в `docs/DEPLOY.md`, модель угроз — в `docs/SECURITY.md`.
Здесь — **организационные** меры: без них защита в коде обходится через людей (Saga, Drift 2026).

## 1. Ключи и multisig (Squads v4)

### 1.1. Два разных multisig — и почему

| | **Admin multisig** (`config.admin`) | **Upgrade multisig** (upgrade authority программы) |
|---|---|---|
| Что может | `propose` / `cancel` / `execute` (параметры, смена admin, траты казны) и `set_pause` | заменить код программы, то есть сделать **что угодно** |
| Защита в программе | `propose` → timelock ≥ 48 ч, который нельзя уменьшить (`MIN_TIMELOCK_SECS`) → `execute(expected_nonce)`; пауза не двигает средства | нет: загрузчик BPF не знает про наш timelock |
| Порог | **3 из 5** | **4 из 7** (или 3 из 5 с другим составом) |
| Time lock самого Squads | **0**: программа уже держит 48 ч на всё опасное, а пауза должна срабатывать за минуты | **48 ч** (`time_lock` в настройках multisig): обновление видно публично за двое суток до исполнения |
| Состав | операционная команда студии | основатели + независимые подписанты (юрист, аудитор-партнёр, представитель сообщества) |

Один multisig на обе роли — плохой вариант. Либо пауза будет ждать 48 ч (если включить time lock в Squads),
либо обновление кода пройдёт мгновенно (если не включать). Второе — ровно сценарий Drift 2026: нулевой timelock
плюс социальная инженерия подписантов.

### 1.2. Правила для подписантов (обязательны)

1. Каждый ключ — на **отдельном аппаратном кошельке** (Ledger/Keystone) у **отдельного человека**; ни у кого нет двух ключей.
   Сид-фразы — только на бумаге/металле, в двух географически разных местах; никаких фото, облаков, менеджеров паролей.
2. Подписант **сам** декодирует транзакцию в Squads UI (или `squads-cli`) и сверяет:
   инструкцию, `pending_nonce`, параметры, получателя. Хеш сверяется голосом по второму каналу с другим подписантом.
3. **Никогда** не подписывать: durable-nonce транзакции, подготовленные кем-то ещё; «срочные» просьбы из мессенджера;
   транзакции, которые не декодируются. Срочного у нас нет ничего, кроме паузы, а пауза безопасна по определению.
4. Ротация: при уходе человека из команды его ключ заменяется в течение 72 ч (для Upgrade multisig — через 48-часовой time lock).
5. Раз в квартал — учебная «пауза/снятие паузы» на devnet всеми подписантами admin multisig (проверка, что ключи живы
   и люди помнят процедуру). Цель — 3 подписи за ≤ 30 минут.
6. Ключ keeper — горячий, но у него **нет прав**: он только крутит тики и платит комиссии. На нём держим ≤ 1 SOL.

### 1.3. Когда отказаться от обновлений

После аудита, 3+ месяцев на mainnet без инцидентов и закрытия программы bug bounty первого года — голосование
о `solana program set-upgrade-authority --final`. Программа станет неизменяемой. Ошибки тогда исправляются
только миграцией в новую программу, зато исчезает главный риск — захват upgrade authority.

## 2. Проверяемая сборка (solana-verify)

Цель: любой может убедиться, что байткод on-chain собран из этого репозитория, этого коммита.

```bash
# 1. детерминированная сборка в docker-образе solana-verify (версии закреплены в Anchor.toml / rust-toolchain.toml)
solana-verify build --library-name recursia -- --features mainnet
solana-verify get-executable-hash target/deploy/recursia.so

# 2. деплой именно этого файла через Upgrade multisig (буфер → Squads → upgrade)
solana program write-buffer target/deploy/recursia.so
solana program set-buffer-authority <BUFFER> --new-buffer-authority <UPGRADE_VAULT>

# 3. сверка и публикация верификации (OtterSec API, отображается в Solana Explorer / SolanaFM)
solana-verify get-program-hash <PROGRAM_ID>          # должен совпасть с шагом 1
solana-verify verify-from-repo --remote --program-id <PROGRAM_ID> \
  https://github.com/Leo88q/crispy-eureka --commit-hash <COMMIT> --library-name recursia -- --features mainnet
```

- В описании каждого предложения на обновление в Squads указываются коммит и хеш из шага 1. Подписанты Upgrade multisig
  **сами** пересобирают и сверяют хеш с хешем буфера (`solana program dump <BUFFER>` → `sha256sum`) до подписи.
- IDL публикуется из того же коммита (`anchor idl init/upgrade` через multisig).
- `Cargo.lock` зафиксирован в репозитории (CI-джоб `lockfile`), тулчейн закреплён — иначе сборка не воспроизводима.

## 3. Bug bounty

Политика раскрытия — в `.github/SECURITY.md` (приватный отчёт через GitHub Security Advisories).
После запуска на mainnet программа переезжает на Immunefi (или аналог) с теми же правилами.

| Уровень | Пример | Награда (предложение) |
|---|---|---|
| Critical | кража/заморозка средств игроков или пулов; обход timelock; чеканка/удвоение баланса | 10% средств под угрозой, **от $10 000 до $100 000** |
| High | кража наград конкретного игрока; манипуляция исходом VRF/суперпозиции; блокировка вывода | $2 000 – $10 000 |
| Medium | DoS мира/сезона дольше эпохи; обход лимитов ИИ-разрешений (`AgentPermit`) без кражи | $500 – $2 000 |
| Low | ошибки клиента, ведущие к неверному превью транзакции; утечки, не дающие контроля | $100 – $500 |

- В зоне охвата: программа `programs/recursia`, SDK (построение транзакций), клиент (превью/подпись), keeper.
- Вне зоны: уже известные принятые риски из `docs/SECURITY.md` (раздел «Принятые риски»), атаки, требующие
  ключей multisig, фишинговые клоны сайта, спам-ошибки RPC, экономические стратегии, не нарушающие правил
  (это игра — выигрывать стратегией можно).
- Правила: без атак на mainnet (демонстрация — на devnet/LiteSVM), без публикации до исправления (до 90 дней),
  первый приславший получает награду. Выплата — в USDC/SKR из казны, **через обычную 48-часовую процедуру `propose`**
  (срочных выплат нет, чтобы «багхантер» не стал каналом социальной инженерии).
- Бюджет: резерв в казне не меньше максимальной Critical-награды до конца первого года.

## 4. Аудит

1. **До аудита** (готово): unit-тесты + property-фаззинг математики, LiteSVM-интеграция и stateful-фаззинг,
   эталонная модель и экономическая симуляция, чек-лист `docs/SECURITY.md`, сопоставление каждого пункта с кодом.
2. **Выбор**: минимум один аудитор с опытом Anchor/SPL и игровых экономик (OtterSec, Neodyme, Zellic, Sec3, Accretion,
   Halborn…). Бюджет — по объёму (≈ 8–10 тыс. строк Rust). Второй, более дешёвый проход (конкурсный аудит, например
   Code4rena/Cantina) — после исправлений первого.
3. **Фокус для аудиторов** (передать письменно):
   - инструкции, которые **не блокируются паузой** — `withdraw`, `quantum_observe`/`collapse`, `swap_resolve`/`cancel`,
     `tournament_settle`/`claim`, `close_*`. В случае ошибки в них пауза не поможет, остаётся только обновление через 48 ч;
   - сохранение SKR: `split_tick`, `split_spend`, эмиссия и ребейты эпохи, доля за эффективность, спонсорский и сезонный пулы;
   - ORAO VRF: `read_vrf`, вывод сида при коммите/принятии, невозможность перебросить исход;
   - Харбергер: начисление налога, выкуп, изъятие (foreclose), кулдауны;
   - `AgentPermit`: лимиты трат ИИ-агентов исполняются в программе, а не в промпте;
   - раскладка аккаунтов, `close`, повторная инициализация, `init_if_needed`.
4. **Замороженный коммит**: на время аудита ветка `audit/<дата>`. Все исправления идут отдельными коммитами с номером находки.
5. **Публикация**: отчёт целиком, статус каждой находки (исправлено / принято с обоснованием) — в `docs/audits/`.
   Запуск на mainnet — только без открытых Critical/High.

## 5. Мониторинг

- **Watcher** (`keeper/src/watch.ts`, `npm run watch -w @recursia/keeper`): read-only, без ключей.
  Каждую минуту пересчитывает денежные инварианты по данным RPC (те же, что LiteSVM-тесты проверяют после каждого шага):
  - сезонный пул = пополнено − выплачено;
  - турнирный пул = Σ банков;
  - `claims` покрывает все балансы игроков;
  - хранилище каждого мира покрывает его леджер, Σ pending = reserved;
  - `treasury_seen` ≤ казна;
  - внешнее пополнение пула наград и спонсорского пула только растёт.

  Отдельно следит за управлением: новое предложение (и когда его можно исполнить), смена admin, пауза, смена upgrade authority.
  Алерты уходят в `ALERT_WEBHOOK` (Discord/Slack/Telegram-мост).
- Запускать **минимум два** экземпляра у разных провайдеров с разными RPC. Упавший watcher — тоже инцидент (heartbeat).
- Любое предложение (`PROPOSAL #n`) автоматически публикуется в публичный канал: сообщество видит его за 48 ч до исполнения.
  Предложение, о котором команда не знает, — это **инцидент уровня Critical** (скомпрометирован admin multisig).

## 6. План реагирования на инциденты

### Уровни

| Уровень | Признаки | Реакция |
|---|---|---|
| **SEV-1** | нарушение денежного инварианта (watcher), неизвестное предложение или смена upgrade authority, активная эксплуатация | пауза ≤ 30 мин, все руки |
| **SEV-2** | уязвимость без эксплуатации (bug bounty, аудит), keeper/ORAO стоит > 1 ч, фишинговый клон сайта | ответ ≤ 24 ч |
| **SEV-3** | ошибки клиента, неверные подсказки, деградация RPC | в плановом порядке |

### SEV-1: пошагово

1. **Зафиксировать** (любой, кто увидел): алерт watcher или отчёт → канал инцидентов, назначить ведущего.
2. **Пауза** (admin multisig, 3 подписи): `set_pause(true)`. Пауза блокирует всё, что тратит или двигает чужие средства:
   посадки, покупки, тики, создание миров, предложения SWAP, вступление в турниры, декогеренцию. Она **не** блокирует
   вывод своих средств и расчёты (`withdraw`, наблюдение/коллапс, `swap_resolve`/`cancel`, итоги турниров, возврат аренды):
   деньги игроков не должны застрять. Если уязвимость именно в этих инструкциях, пауза не спасёт. Тогда сразу п. 4.
3. **Неизвестное предложение** в admin multisig: `cancel` (3 подписи) — у нас 48 ч, этого достаточно. Затем ротация
   скомпрометированных ключей через `propose(SetAdmin(new_multisig))` — тоже 48 ч, в течение которых watcher следит.
4. **Исправление**: патч → тесты (unit, LiteSVM, фаззинг, регрессионный тест на саму атаку) → быстрый ревью аудитора →
   проверяемая сборка (раздел 2) → предложение в Upgrade multisig. Squads time lock 48 ч **не обходится**:
   если что-то нужно «прямо сейчас», значит, пауза не сработала, и это надо признать публично, а не ускорять подписи.
5. **Коммуникация**: первое сообщение ≤ 1 ч после паузы — что известно, что с деньгами игроков, что делать
   (обычно: ничего не подписывать, остерегаться «компенсационных» сайтов — это стандартный следующий шаг атакующих).
   Обновления — каждые 6 ч, даже если новостей нет.
6. **Снятие паузы** — только после обновления, сверки watcher (0 нарушений) и публичного отчёта.
7. **Разбор** ≤ 7 дней: хронология, причина, что изменено в коде и процессах; публикуется в `docs/incidents/`.
   Компенсации — отдельным предложением через обычный timelock.

### Шаблон первого сообщения

> RECURSIA приостановлена (пауза в контракте) в HH:MM UTC из-за [кратко]. Вывод ваших SKR работает, средства в пулах
> [не затронуты / затронуты на N SKR — выясняем]. **Ничего не подписывайте** по ссылкам из сообщений — мы не
> рассылаем «компенсации» и не просим подключить кошелёк. Следующее обновление — в HH:MM UTC.

## 7. Домен и фронтенд

DNSSEC, registry lock, CAA, HSTS preload, 2FA на аккаунтах регистратора и хостинга с аппаратными ключами —
см. `docs/DEPLOY.md`, раздел «Домен». Захват DNS (урок Curve/Balancer) — SEV-1: пауза не нужна, но нужно
немедленное публичное предупреждение и откат DNS.
